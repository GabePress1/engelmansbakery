# Workflows

n8n workflow exports. These live in n8n under
`My project / Engelman's Bakery / Printing Letter_Invoices`.

## Emailing Letter + Statement Draft Workflow

Creates an **unsent Outlook draft** per account with **two attachments**:

| Attachment | Source |
|---|---|
| `Letter_<account>_<date>.pdf` | `Printing Letter_Invoices` — billing page, plus shipping page when the addresses differ |
| `Statement_<account>_<date>.pdf` | Business Central, rendered once per account |

One letter document, one statement document. The statement is never duplicated, because it is
rendered fresh from BC rather than taken from the printed pack.

Nothing is ever sent. The workflow contains no `send` operation — only `draft: create`.

### Importing it into n8n

This repo holds the workflow as a JSON export. It does not exist in n8n until you import it:

1. In n8n, open the **Engelman's Bakery / Printing Letter_Invoices** folder.
2. **Create workflow**.
3. Top-right **⋮** menu → **Import from File…**
4. Pick `workflows/emailing-letter-statement-draft.json`.
5. Save. It appears as **Emailing Letter + Statement Draft Workflow**.

The JSON is generated by `tools/build_workflow.py` — edit that and re-run it rather than hand
editing the export, since the Code nodes are easier to get right unescaped.

### Running it

1. Open the workflow and click into **ERP Account Number (Filter)**.
2. Type the ERP account number — e.g. `10981` — into `erpAccountNumber`.
3. Click **Execute workflow**.
4. The draft appears in **gpress@engelmansbakery.com**'s Drafts, addressed to that account's AP
   contact, with the letter and statement attached.

Nothing is sent. Open the draft, check it, and send it yourself.

Leave `erpAccountNumber` **blank** to draft for every account `Printing Letter_Invoices` returns.

### Flow

```
Manual trigger
  └─ ERP Account Number (Filter)           ← type the account number here
       └─ Printing Letter_Invoices         (one item per address variant)
            └─ Normalize Letter Item
                 └─ Letter PDF → Base64
                      └─ Matches ERP Filter?
                           ├─ false ─ Filtered Out — Different Account
                           └─ true ── Group Letters by Account   ← one item per account
                                └─ Require Account Number
                                     └─ Look Up AP Contact (Business Central)
                                          └─ Attach Contact Email
                                               └─ Has Email on File?
                                                    ├─ false ─ Skipped — No Email on File
                                                    └─ true ── Render Statement PDF (BC)
                                                         ├─ error ─ Statement Not Rendered — Review
                                                         └─ ok ──── Merge Letter PDFs
                                                              └─ Build Draft Payload
                                                                   └─ Attach Letter + Statement PDFs
                                                                        └─ Create Outlook Draft (Do Not Send)
                                                                             └─ Drafts Ready for Review
```

### Billing and shipping addresses

`Printing Letter_Invoices` returns **one item per address variant** — billing, then shipping when
it differs. Two nodes handle that:

- **`Group Letters by Account`** collapses those items to one per account. Without it, an account
  with two addresses would produce two drafts, two statement calls, and the statement twice.
- **`Merge Letter PDFs`** concatenates the variants into a single letter PDF, billing page first.

A single-address account passes straight through the merge and needs nothing extra. Only accounts
with *differing* billing and shipping addresses actually merge, and that path needs the `pdf-lib`
module — set `NODE_FUNCTION_ALLOW_EXTERNAL=pdf-lib` on the n8n instance. If it is unavailable the
node fails with that instruction, and single-address accounts keep drafting normally.

### The account number is the join key

Business Central is the system of record, and every piece of the email is tied together by the
customer account number:

| Piece | Keyed on account number via |
|---|---|
| Letter PDF | `Printing Letter_Invoices` items, grouped on `accountNumber` |
| Email address | `$filter=Integration_Customer_No eq '<accountNumber>'` against BC contacts |
| Statement PDF | `customerNo` posted to the BC `StatementApi` codeunit |

`Require Account Number` throws if the key is missing. Without it an empty `$filter` would match
every contact in the company, and the statement would be rendered for the wrong account.

### Where the recipient address comes from

```
Customer Card  10981 · Berkeley Hills Country Club
  └─ Integration Customer No. ──→ Contact CT020141   (Contact table 5050, "ATTN: Accts Payable")
                                    └─ E-Mail  ← the address the draft goes to
```

`Look Up AP Contact (Business Central)` queries the **Contact List** page (5052) published as an
OData V4 web service named `ContactList`:

```
GET .../ODataV4/Company('{BC_COMPANY_NAME}')/ContactList
    ?$filter=Integration_Customer_No eq '10981' and Business_Relation eq 'Customer'
    &$select=No,Name,Company_Name,E_Mail,Integration_Customer_No
```

If more than one contact matches, `Attach Contact Email` prefers the first with an actual email.
The match count rides along as `contactMatchCount`, so a zero-match account is diagnosable from
the skip branch.

### Where the statement comes from

Business Central **cannot** return a report as a PDF over a plain OData query — `$format=PDF` is
not supported on report web services. The PDF has to be rendered in AL and handed back as text, so
this repo ships a small codeunit for it:

**`businesscentral/StatementApi.Codeunit.al`** — renders a statement report, scoped to one
customer, and returns it base64 encoded.

The report is **passed in, not hardcoded**, so the custom statement Engelman's actually prints
stays the source of truth and can change without redeploying the extension. There is deliberately
no default — a missing ID errors out rather than quietly sending customers a statement in the
wrong layout.

Set `BC_STATEMENT_REPORT_ID` to **`50042`**, the custom statement report Engelman's prints.

Deploy the codeunit and publish it as a web service:

| Web Services page field | Value |
|---|---|
| Object Type | `Codeunit` |
| Object ID | `50100` |
| Service Name | `StatementApi` |
| Published | yes |

The workflow then calls it as an OData V4 unbound action:

```
POST .../ODataV4/StatementApi_GetCustomerStatementPdf?company={BC_COMPANY_NAME}
{ "customerNo": "10981", "reportId": 50042, "requestPageXml": "" }

→ { "value": "<base64 pdf>" }
```

**Scoping.** The statement report is built over `Cust. Ledger Entry`, so that is the table the
codeunit filters and hands to `Report.SaveAs` as a `RecordRef`. Filtering `Customer` instead would
not scope the report at all — every account would come back in one PDF.

**Open items only** is enforced by that same filter:

```al
CustLedgerEntry.SetRange("Customer No.", customerNo);
CustLedgerEntry.SetRange(Open, true);      // open items only
```

Because the filter does it, `BC_STATEMENT_REQUEST_XML` is only needed for *other* request page
options (a date range, a layout choice). An empty string is fine and is the expected default.

**Customers with nothing outstanding.** The codeunit errors rather than producing an empty
statement. That error is routed to `Statement Not Rendered — Review` instead of aborting the run,
so one such account does not stop the rest of the batch from drafting.

### Before first run

**Three credential/ID placeholders:**

| Node | Placeholder | Replace with |
|---|---|---|
| `Printing Letter_Invoices` | `REPLACE_WITH_PRINTING_LETTER_INVOICES_WORKFLOW_ID` | that workflow's n8n ID |
| `Look Up AP Contact` / `Render Statement PDF` | `REPLACE_WITH_BUSINESS_CENTRAL_OAUTH2_CREDENTIAL_ID` | a generic OAuth2 credential for the BC API (both nodes) |
| `Create Outlook Draft (Do Not Send)` | `REPLACE_WITH_OUTLOOK_CREDENTIAL_ID` | the Outlook OAuth2 credential for **gpress@engelmansbakery.com** |

The draft is created in whichever mailbox owns the Outlook OAuth2 credential, so that credential
must be gpress@engelmansbakery.com.

**Five project Variables** (Project settings → Variables):

| Variable | Value |
|---|---|
| `BC_TENANT_ID` | your Entra tenant GUID |
| `BC_ENVIRONMENT` | `Production` |
| `BC_COMPANY_NAME` | the BC company name, as it appears in the OData URL |
| `BC_STATEMENT_REPORT_ID` | `50042` |
| `BC_STATEMENT_REQUEST_XML` | leave empty |

**Two BC prerequisites:**

- Contact List page (5052) published as a web service named `ContactList`.
- `Statement Api` codeunit (50100) deployed and published as `StatementApi`.

**One n8n prerequisite**, only for accounts with differing billing and shipping addresses:
`NODE_FUNCTION_ALLOW_EXTERNAL=pdf-lib`.

### Assumptions

- `Printing Letter_Invoices` returns the letter as **binary PDF data**, one item per address
  variant, each carrying the customer number.
- **Those letter PDFs contain the letter only.** If they still have statement pages bundled in —
  as the printed pack does today — the statement will appear twice in the email: once inside the
  letter attachment and once as the statement attachment. See *Open questions* below.
- `accountNumber` resolves to the customer number (e.g. `10981`).
- `Integration_Customer_No` and `Business_Relation` are the Contact record's OData field names
  (confirmed).

### Open questions

- **Do the letter PDFs still include the statement?** The printed pack bundles address + statement
  into each PDF. This workflow attaches the letter PDF as-is and adds a separately rendered
  statement, so if the bundling is still there the customer gets the statement twice. Either
  `Printing Letter_Invoices` emits letter-only PDFs for this path, or this workflow needs to trim
  the statement pages off before attaching.
- **The email body.** The letter arrives as a PDF, which cannot be an HTML body, so the body is a
  short cover note and the letter is read from its attachment. If `Printing Letter_Invoices` also
  emits letter text, `Build Draft Payload` uses that for the body instead.

### Notes

- Three review branches. `Skipped — No Email on File` and `Statement Not Rendered — Review` both
  mean a customer did *not* get chased — check them after every run. `Filtered Out — Different
  Account` is normal traffic on a single-account run; only worry if *everything* lands there,
  which means the ERP number matched nothing.
- `Has Email on File?` requires the address to be non-empty *and* contain `@`.
- The letter PDF is carried through the HTTP nodes as base64 in JSON, because binary data does not
  survive them whereas JSON does. It is turned back into a PDF in `Attach Letter + Statement PDFs`.
- The ERP filter is applied *after* `Printing Letter_Invoices` runs, which avoids assuming
  anything about that workflow's input contract.
- Both BC calls retry 3 times with a 2s backoff on transient failures.
