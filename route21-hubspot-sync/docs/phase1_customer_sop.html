Phase 1 – Business Central → HubSpot Companies Final

System: n8n Cloud — engelmansbakery.app.n8n.cloud Workflow ID: 2HLvAAkFmeKkhHg0 Last Updated: June 2026

Purpose

This workflow keeps HubSpot company records synchronized with Business Central (BC) customer data. It runs automatically every weekday morning (Monday–Saturday) and can also be triggered manually. It pulls financial, address, route, delivery schedule, salesperson, and payment data from BC and writes it into the matching HubSpot Company record — matched by ERP Account Number.

This workflow does not create new HubSpot companies, delete records, or write back to BC.

BC Data Sources

Data is pulled from three separate BC endpoints each run. Each source has a different scope and frequency.

Source A OData · Ship-to Address List
Source B Standard API v2.0 · Customers (changed only)
Source C OData · Customer Table (balance, route, calendar)

If a customer has not changed in BC, their name, billing address, payment terms, salesperson, and blocked status will not be re-pushed to HubSpot that day — the existing HubSpot values are preserved.

Step-by-Step Flow

Stage 1 — Setup (Runs Once Per Execution)
1
Keys Loads BC credentials: Tenant ID, Client ID, Client Secret, and Company ID. All downstream BC calls reference this node — credentials only need to be updated here.
2
Get BC Token Calls Microsoft Azure AD to obtain a Bearer token for the BC API. Valid for 60 minutes and used for the initial BC calls before the batch loop begins.
3
Set Window Reads the timestamp of the last successful run from n8n's persistent memory. Saves today's timestamp for the next run. This window controls which BC customers are treated as "changed" and returned by the customer fetch.
4
HTTP Request — Get All Ship-to Addresses Fetches up to 5,000 ship-to (delivery) addresses from the BC OData page ShiptoAddressList. Retrieved in full every run because ship-to changes are not reflected in the customer's modified date.
5
Store Ship-to Data Builds an in-memory lookup of ERP number → first ship-to address. Only the first ship-to record per customer is kept. Stored in memory for use during batch processing.
6
Fetch Changed BC Customers Calls the BC Standard API v2.0 /customers endpoint filtered to only customers whose lastModifiedDateTime is newer than the last run timestamp. Returns name, billing address, payment terms, payment method, credit limit, blocked status, and salesperson code.
7
Store BC Customer Data Stores the changed customer records in memory, keyed by ERP number. This becomes the customerMap used in Process Batch. Customers not modified since the last run will not appear here.
Stage 2 — Loop 1: Collect All HubSpot Companies
8
Initialize HS Fetch → Build HS Search Payload → Search HubSpot Companies → Accumulate HS Results → More HS Pages? Paginates through HubSpot's CRM search API (200 companies per page) collecting all companies that match all three criteria:
  • Relationship = Customer
  • Division includes Engelman's Bakery
  • ERP Account Number field has a value
Repeats until all pages are collected, then continues to Stage 3.
Stage 3 — Loop 2: Process Each Batch of 100
9
Expand HS Companies → Loop 2 Batches Splits all collected HubSpot companies into groups of 100. Processes one group at a time. When all batches are complete, exits to Sync Summary.
10
Build Calendar Filter Constructs a BC OData filter for the 100 ERP numbers in the current batch — e.g., No eq '10001' or No eq '10002' or ... — so only the relevant customers are returned by the BC API.
11
Refresh BC Token Fetches a brand-new BC API token before every batch. BC tokens expire after exactly 60 minutes; because the full workflow can run longer than that, refreshing every batch ensures no batch ever fails due to an expired token.
12
HTTP Request — Get Calendar & Balance Fetches live balance, route, and delivery schedule data for every ERP number in the batch from the BC OData Customer page. Runs for every customer on every run — not just recently modified ones.
13
Process Batch Core logic: combines data from all three BC sources and maps it to HubSpot properties. Applies route translation, delivery calendar parsing, payment method label mapping, and salesperson-to-Company-Owner assignment. Only fields with a value (or fields that must be cleared) are included in the update payload.
14
Has Updates? → Batch Update HubSpot → Loop back If any companies in the batch have changes, sends a single PATCH batch request to the HubSpot CRM API updating up to 100 companies at once. Then loops back to step 9 for the next batch of 100.

Important Notes

RT 14 is intentionally excluded from the route map.
Route 14 may be either "14a – Augusta" or "14b – Chattanooga" depending on the customer. Because BC cannot distinguish between them, the workflow leaves the HubSpot route field unchanged for any customer assigned to RT 14.
payment_terms_code and payment_method_code are always cleared when BC is blank.
These two fields behave differently from the others. If a customer's payment term or method is removed in BC, the workflow will clear those fields in HubSpot on the next run that includes that customer in the delta. This is intentional — it keeps HubSpot from showing stale payment info.
Company Owner only updates when the salesperson code changes in BC.
Because salesperson code comes from Source B (delta only), the Company Owner in HubSpot is only updated when the BC customer record is modified. If a salesperson reassignment is made directly in HubSpot, it will be overwritten the next time that customer's BC record changes.
Billing address vs. shipping address.
This workflow writes two separate address sets. Billing address (billing_street_address, billing_city, etc.) comes from the BC customer record. Shipping/delivery address (address, city, zip) comes from the Ship-to Address List and reflects where orders are physically delivered.
Country field is not synced from BC.
The HubSpot country property is not written by this workflow. Whatever value exists in HubSpot will remain untouched.
