Purpose

Phase 1 is a nightly one-way sync from Business Central (BC) to HubSpot CRM. It reads customer account data from BC and writes it to the corresponding Company record in HubSpot, matched by the erp_account_number property. It does not read or write anything from HubSpot back to BC.

The sync is intentionally incremental on the BC customer side — only customers modified since the last run are re-fetched. Balance, route, delivery schedule, and shipping address are fetched fresh for every customer on every run.

Scope: This SOP covers Phase 1 only. Ordering status, invoice analytics, and deal-related fields are handled by separate workflows and are never touched by this workflow.

Get BC Token HTTP Performs a client-credentials OAuth2 request to Microsoft's token endpoint (login.microsoftonline.com). Returns a Bearer token valid for 3600 seconds (60 minutes). This token is used for all initial BC calls (Ship-to addresses, Fetch Changed Customers). Note: A separate token refresh runs inside the batch loop — see Refresh BC Token.
Set Window Code Reads lastPhase1Run from workflow static data (persists between runs). Records the current timestamp as the new lastPhase1Run. The previous timestamp (lastTimestamp) is passed to the BC customer fetch as a delta filter — only customers modified after that time are re-downloaded. On the very first run, the fallback is 2000-01-01, which returns all customers.
HTTP Request – Get All Ship-to Addresses HTTP Calls the BC OData v4 ShiptoAddressList endpoint. Fetches up to 5,000 ship-to records across all customers (fields: HFSCustomerNo, Address, Address_2, City, Post_Code). This is fetched in full every run because ship-to changes are not surfaced in the standard customer modified date.
Store Ship-to Data Code Iterates the ship-to rows and builds a lookup map keyed by HFSCustomerNo. Only the first ship-to record per customer is kept (primary delivery address). Saves the map to workflow static data as shipToMap for use in Process Batch.
Fetch Changed BC Customers HTTP Calls the BC Standard API v2.0 /customers endpoint filtered to lastModifiedDateTime gt {lastTimestamp}. Returns up to 5,000 customers with billing address, payment terms, payment method, credit limit, blocked status, and salesperson code. Using a delta filter keeps this call fast on subsequent runs — typically only a handful of customers have changed overnight.
Store BC Customer Data Code Converts the customer array into a lookup map keyed by ERP account number (customerMap) and saves it to static data. This avoids repeated array scans inside the batch loop.
Initialize HS Fetch Code Clears the HubSpot accumulator arrays in static data (hsCompanies, hsCursor) before pagination begins. Ensures a clean state even if the workflow is re-run the same day.
Build HS Search Payload Code Constructs the HubSpot CRM search request body. Three filters are applied simultaneously: relationship EQ Customer, division_multiselect CONTAINS "Engelman's Bakery", and erp_account_number HAS_PROPERTY. This ensures only Engelman's active customer companies with an ERP number are targeted — not prospects, not other divisions. Returns 200 companies per page. If a pagination cursor exists in static data, appends it as after.
Search HubSpot Companies HTTP Posts the search payload to HubSpot's /crm/v3/objects/companies/search API. Returns up to 200 company records per call including hs_object_id, erp_account_number, and name.
Accumulate HS Results Code Appends the current page of results to store.hsCompanies. Checks whether HubSpot returned a paging.next.after cursor indicating more pages exist. Sets hasMore = 1 if so, 0 if this was the last page.
More HS Pages? If Branches on hasMore. True (hasMore > 0): loops back to Build HS Search Payload to fetch the next page. False: all companies have been collected — proceeds to Expand HS Companies. This loop runs as many times as needed; a 500-company dataset requires 3 iterations at 200 per page.
Expand HS Companies Code Reads the full hsCompanies array from static data and emits each company as an individual n8n item. This converts the accumulated array into a stream of items that the batch splitter can divide.
Loop 2 Batches Loop Splits all HubSpot companies into groups of 100 and processes one group at a time. Has two outputs: Done (all batches processed → Sync Summary) and Batch (current 100 companies → Build Calendar Filter). Iterates until every company has been processed.
Build Calendar Filter Code Reads the current 100 HubSpot companies from $input.all(). Saves them as store.currentBatch for use in Process Batch. Builds an OData filter string in the form No eq '12345' or No eq '12346' or ... for the 100 ERP numbers, which is passed to the BC Calendar & Balance request so only the relevant records are returned.
Refresh BC Token HTTP Fetches a fresh BC OAuth2 token on every batch iteration. Required because the workflow runs for ~65 minutes but BC tokens expire after exactly 60 minutes. Without this node, batches processed after the first hour would receive 401 Unauthorized errors from BC. The refresh adds ~300ms per batch (negligible) and completely eliminates the expiry risk.
HTTP Request – Get Calendar & Balance HTTP Calls BC OData v4 /Customer endpoint filtered to the 100 ERP numbers in the current batch. Returns Balance_LCY, Balance_Due_LCY, Shipping_Agent_Code, and Base_Calendar_Code. These fields are not available in the Standard API v2.0, which is why the OData endpoint is used here.
Process Batch Code The core transformation node. For each of the 100 HubSpot companies in the current batch, it looks up BC data from three sources (OData Calendar/Balance response, customerMap, shipToMap), applies translation maps (route, payment method, salesperson), and assembles a HubSpot property payload. Only changed/populated fields are included. See the Field Mapping section below for exact behavior.
Has Updates? If Checks whether updateCount > 0. If no properties changed for any company in the batch (e.g., all 100 companies have no BC data), the HubSpot update call is skipped entirely to avoid unnecessary API calls. Either path returns to the loop for the next batch.
Batch Update HubSpot HTTP Posts to HubSpot's /crm/v3/objects/companies/batch/update API with up to 100 company updates in a single call. Uses continueOnFail: true — if HubSpot rejects one batch, the loop continues to the next batch rather than halting the entire workflow.
Sync Summary Code Runs once after all batches are complete. Clears all temporary static data (hsCompanies, customerMap, shipToMap, currentBatch) to free memory. Returns a summary item with the total number of companies processed.

How All HubSpot Companies Are Obtained

HubSpot's search API returns a maximum of 200 records per request. The workflow uses a cursor-based pagination loop to collect every matching company regardless of total count:

  1. Initialize HS Fetch clears any leftover state from a prior run.
  2. Build HS Search Payload constructs the request. If a cursor exists in memory, it is appended as after.
  3. Search HubSpot Companies posts the request and returns up to 200 results plus an optional paging.next.after value.
  4. Accumulate HS Results appends results to the in-memory array and records the cursor.
  5. More HS Pages? routes back to step 2 if a cursor was returned, or forward to Expand HS Companies if this was the last page.

Filter criteria applied to every search page:

  • relationship = Customer — excludes prospects and vendors
  • division_multiselect contains "Engelman's Bakery" — scopes to this division only
  • erp_account_number has property — excludes HubSpot companies that have never been linked to a BC account

Tip: To verify how many companies the workflow will touch, run a HubSpot company search manually with these three filters applied. The count should match the totalProcessed value in the Sync Summary node output.

What Happens When a BC Field is Blank

The general rule is if BC is blank, HubSpot is not touched — the existing HubSpot value is preserved. There are three deliberate exceptions:

payment_terms_code — Always written when a customer appears in the delta, even if BC has no payment term. If BC is empty, HubSpot is cleared to null. This is intentional: if a payment term is removed in BC, it should be removed in HubSpot too.

payment_method_code — Same behavior as payment_terms_code. Also cleared to null if the BC code is unrecognized (not in the translation map).

blocked — Always written as either "Blocked" or "" (empty string). When an account is unblocked in BC, the HubSpot field is actively cleared.

Important — Delta behavior: Standard API fields (billing address, name, payment terms, salesperson, etc.) are only updated in HubSpot when the customer's lastModifiedDateTime in BC is newer than the last workflow run. If a customer record has not changed in BC since the previous night, none of its Standard API fields will be written to HubSpot — even if those fields are blank in HubSpot. OData fields (balance, route, calendar, ship-to address) are written on every run for every customer, regardless of modification date.
